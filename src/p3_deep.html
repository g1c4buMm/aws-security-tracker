Threat detectionGuardDutyOct 1

Amazon GuardDuty: centralized enablement with AWS Organizations declarative policies

An organization policy now enables GuardDuty across every account and Region. The configuration applies to existing accounts and is maintained automatically as new accounts join.

Architecture
GuardDuty policyDefined from the delegated administrator account
→
Attach pointOrganization root, OUs or individual accounts
→
Default configApplies in every Region where GuardDuty is available
→
Per-Region overridesFor Regions that need different enablement
Key facts
Override
Policy-set enablement cannot be changed from the GuardDuty console or API
New accounts
Covered automatically when they join the organization
Availability
All commercial Regions and AWS GovCloud (US)
Setup
GuardDuty console → Organization policies, or the AWS Organizations APIs
LATAM contextFinancial groups in Brazil and Mexico often run hundreds of accounts across several Regions. A single policy replaces per-Region enablement scripts and closes the drift that auditors find when a new account goes live without threat detection.
Threat detectionGuardDutyOct 2

GuardDuty Runtime Monitoring is now included in the Security Hub Threat Analytics plan

Runtime Monitoring inspects operating system, network and file activity to surface container escapes, privilege escalation and cryptomining. Where Security Hub is enabled, this usage now bills under Security Hub instead of GuardDuty.

What changes and what stays

Changes

  1. No separate GuardDuty charge for Runtime Monitoring in accounts and Regions with Security Hub enabled
  2. One Security Hub usage type spanning EC2, EKS and ECS on Fargate

Stays the same

  1. Detection coverage and finding types
  2. GuardDuty security agents, with no reconfiguration
  3. Free trials: Threat Analytics and Essentials stay separate, no new trial
LATAM contextTeams that budget security tooling per service should check Cost Explorer or the Security Hub usage page this month: the line item moves from GuardDuty to Security Hub.
IdentityIAM Identity CenterSep 30

Identity Store APIs now accept resource ARNs in addition to resource IDs

Anywhere the Identity Store APIs took the ID of a user, group, group membership or identity store, they now also accept its ARN. The change is additive: existing integrations keep working.

Before vs. after

Before: parse the ID out of the ARN

USER_ARN="arn:aws:identitystore::123456789012:user/user-abc123"
USER_ID=$(echo $USER_ARN | awk -F'/' '{print $NF}')
aws identitystore describe-user \
  --identity-store-id d-9067f23abc \
  --user-id $USER_ID

After: pass the ARN

USER_ARN="arn:aws:identitystore::123456789012:user/user-abc123"
aws identitystore describe-user \
  --identity-store-id d-9067f23abc \
  --user-id $USER_ARN
LATAM contextProvisioning pipelines that pass ARNs between CloudFormation, CDK and access-review tooling can drop their parsing step, which removes one more place for a joiner-mover-leaver flow to break.
IdentityAWS Account ManagementSep 30

AWS accounts now support phone number verification

Primary contact phone numbers were only checked for format. They can now be verified out of band with an SMS one-time passcode, in the console or through the API.

Verification flow
  1. Call SendPhoneNumberVerification (or start from the console) to send a 6-digit OTP by SMS.
  2. Submit the code with VerifyPhoneNumber.
  3. Read the status with GetContactInformation.
  4. Changing the number with PutContactInformation asks for verification again.
Key facts
Organizations
Member accounts inherit verified status when they use the management account's number
Availability
All AWS commercial Regions
LATAM contextIncident response plans depend on AWS reaching the right person. A verified primary contact is a quick hygiene item to add to account baselines across the organization.

PostureCloudTrailSep 30

CloudTrail Event Coverage uncovers blind spots in data plane logging

A new console experience shows, at account and organization level, which services and resource types have data event logging enabled and which do not, and lets you subscribe to the missing coverage from the same view.

Closing a gap from the CLI
# Example: add S3 object-level data events to an existing trail
aws cloudtrail put-event-selectors \
  --trail-name org-trail \
  --advanced-event-selectors '[{"Name":"S3 data events","FieldSelectors":[
    {"Field":"eventCategory","Equals":["Data"]},
    {"Field":"resources.type","Equals":["AWS::S3::Object"]}]}]'
LATAM contextWhen a regulator or auditor asks whether access to personal data is logged, the coverage view turns the answer into a checklist per service and resource type instead of a manual inventory.
PostureSecurity HubOct 1

Security Hub remediation plans prioritize and fix exposures by root cause

Remediation plans group exposure findings that share a root cause. Fixing the one underlying resource, such as a misconfigured setting or an overly permissive policy, resolves or lowers the severity of several exposures at once.

Architecture
Exposure findingsMany findings on related resources
→
Root-cause groupingOne plan per underlying issue
→
Remediation stepsCLI, Terraform and CDK guidance
→
API accessPlans can be consumed by AI agents and automation
Key facts
Unit of work
The root cause, not the individual finding
Pricing
No additional cost in Security Hub Essentials
LATAM contextLean security teams can work a short list of root causes instead of a long list of findings, and keep the fixes as reviewed infrastructure as code.

Security teams can detect and block malicious DNS traffic from their VPCs with PANW Advanced DNS Security rules, without deploying separate firewalls or changing VPC configuration. Generally available in 32 AWS Regions, after a preview that started in June.

Control plane, video ingestion and playback traffic stays on the AWS network through interface VPC endpoints, with no internet gateway, NAT device or public IP.

After

Key facts

VPC endpoint policies
Availability

LATAM contextVideo from branches and ATMs often carries personal data. Keeping it off the public internet removes NAT and public IPs from the design and narrows the attack surface.

Data protectionS3Oct 1

S3 Object Lock variable retention with event holds now in AWS GovCloud (US)

Variable retention applies WORM protection to objects whose retention period starts with a future event, such as a contract closing or an audit completing. It launched in commercial Regions on September 8 and now reaches GovCloud (US-East) and GovCloud (US-West).

How event holds work
Event holdPlaced with a retention duration
→
ProtectedWORM while the hold is in place
→
ReleaseThe triggering event happens
→
Retention clockObject kept for the specified duration
Key facts
vs. legal hold
A legal hold ends protection on removal; an event hold starts the retention period
Assessment
Cohasset Associates: SEC 17a-4(f), FINRA 4511, CFTC 1.31
LATAM contextRecord-keeping rules that count retention from the end of a contract or relationship fit this model directly, without keeping data longer than policy requires. In LATAM, use the commercial-Region launch from September 8.

Week 40 in one paragraph

Enforcement got harder to bypass (GuardDuty organization policies), visibility gaps got easier to see (CloudTrail Event Coverage, Secrets Manager recommendations, DNS analytics), and fixes got grouped by root cause (Security Hub remediation plans). For LATAM teams, the practical starting point is the GuardDuty policy plus remediation plans: a uniform detection baseline, then a short list of root causes to fix.
